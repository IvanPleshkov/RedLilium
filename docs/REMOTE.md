# Remote control (editor automation)

Канал управления редактором для инструментов и агентов (в первую очередь —
Claude): текстовый протокол, через который можно читать состояние сцены,
совершать undo-able правки и снимать скриншоты. Дизайн-цели: пригодность для
слабых моделей (плоские текстовые команды, предсказуемые ответы), соблюдение
редакторской гарантии (все правки — через `EditAction` → история), явная
асинхронность ассетов.

## Транспорт

- TCP на localhost; порт выбирается ОС и публикуется в `.redlilium/editor.port`.
- Включается только `REDLILIUM_REMOTE=1` (по умолчанию канала не существует).
- Сеть обслуживается IO-рантаймом движка (тем же tokio, что грузит ассеты):
  транспорт — `RemoteTransport` (ресурс) + `RemoteServe` (система), движковый
  уровень (`ecs/std/remote.rs`); семантика команд — в редакторе
  (`editor/src/remote_commands.rs`).
- Это dev-инструмент: без аутентификации, не игровой неткод.

## Формат

Одна строка — один запрос; одна строка — один ответ. Всё — RON.

```
(id: 1, cmd: "inspect", entity: "12@3")
(id: 1, ok: true, entity: "12@3", components: [("Transform", (translation: (…), …)), …])
```

- `id` — корреляция; ответы приходят по порядку в рамках соединения.
- Ошибка: `(id: N, ok: false, error: "…")`. Неизвестная команда — ошибка,
  не обрыв.
- **Естественный RON**: данные компонентов — обычные RON-значения (то, что
  написал бы человек), без внутреннего тегированного дерева и без
  строкового экранирования. Числа терпимы к форме (`1` / `1.0`) — serde
  приводит к типу поля. Ссылки на сущности: `(__entity: "index@tick")`.
- Сущности адресуются как `"index@spawn_tick"` (стабильно в рамках сессии;
  видно в `state`).

## Семантика исполнения

- **Записи** (`edit_component`, `add_component`, `remove_component`,
  `select`, `action`) строят те же `EditAction`'ы, что и UI, и идут через
  `ActionQueue` → историю (undo работает). Ответ приходит **после
  применения** (следующий кадр) и несёт свежий снапшот затронутого
  компонента. Результат применения протаскивается в ответ: если `apply`
  упал (кривые данные, мёртвая сущность) — придёт `ok: false` с ошибкой,
  а не ложный ack.
- Ответ на запись НЕ означает, что ассеты доехали. Асинхронность явная:
  `wait(for: "assets_idle")` ждёт, пока ассет-пайплайн будет спокоен
  несколько кадров подряд. Рецепт проверки: `edit` → `wait assets_idle` →
  `screenshot`/`inspect`.
- **Чтения** отвечают в том же кадре.

## Команды (proto 1)

| Команда | Параметры | Ответ |
|---|---|---|
| `hello` | — | `proto`, `commands` |
| `state` | — | `scene` (текущая сцена, `"mount/path"` \| None), `entities: [(entity, name, parent, components)]`, `selection`, `game: Some((hosted, behavior_override, stale, rebuilding, restart_required, schema_diverged))` — статус захосченной игры (ADR-037): `hosted: "static"\|"dylib"\|"none"`; `stale` — исходники игры менялись после последней сборки; `rebuilding` — фоновый `cargo build` идёт; `restart_required` — свежий cdylib собран против изменившегося движка (fingerprint-гейт отказал в загрузке) — нужен рестарт бинаря (Tier 2); `schema_diverged` — схемы компонентов behavior-модуля разошлись со статическим образом (play на новом коде, авторинг новых полей — после рестарта) |
| `inspect` | `entity` | `components: [(имя, натуральный RON)]` |
| `edit_component` | `entity`, `component`, `data: <RON>` | снапшот компонента после применения |
| `add_component` / `remove_component` | `entity`, `component` | ack после применения |
| `select` | `entities: […]` | ack после применения |
| `undo` / `redo` | — | ack / ошибка |
| `logs` | `since` (seq) | `entries: [(seq, level, target, message)]` |
| `wait` | `for: "assets_idle"` (+`timeout_ms`) \| `for: "frames"`, `n` | ack по условию / timeout |
| `step` | `n` (default 1) | ack после N кадров |
| `screenshot` | `target: "scene"`, `path` | `path`, `width`, `height` — PNG написан на диск |
| `shutdown` | — | ack; редактор завершается |
| `action` | `name`, `params: (…)` | ack после применения; spawn-действия возвращают `entities` |
| `actions` | — | `[(имя, usage)]` — интроспекция реестра |
| `new_asset` | `source`, `kind`, `dir?`, `name?` | `guid`, `path` — файл + запись в DB; `kind: "scene"` создаёт валидную пустую сцену (открывается через `load_scene`) |
| `save_prefab` | `entity`, `path` | ack — поддерево записано как `.prefab` (RON) |
| `spawn_prefab` | `path`, `parent?` | `entities` после применения (undoable) |
| `save_scene` | `path?` (default — текущая сцена) | `path` — контент мира (без editor-сущностей) записан как `.scene`; путь становится текущей сценой |
| `load_scene` | `path` | ack после применения (undoable) — замена контента мира на сцену; editor-сущности переживают, undo возвращает прежний контент |
| `pick` | `x`, `y` | `entity: Some("i@t")` \| `None` — сущность под точкой |
| `pick_rect` | `x`, `y`, `w`, `h` | `entities` — все сущности в регионе |
| `set_gizmo_mode` | `mode: "translate"|"rotate"|"scale"` | ack — переключение режима трансформ-гизмо (не undoable) |
| `reload_game` | — | ack = запрос принят. **Game-owned редактор с behavior_reload (ADR-037 Tier 1):** фоновая пересборка cdylib игры фиксированной инвокацией; по зелёному билду behavior-модуль свапается (живая play-сессия останавливается), следующий `play` идёт на новом коде, мир редактирования не трогается вовсе. Прогресс/результат — поля `game` в `state` (`rebuilding` → `behavior_override`/`restart_required`) и лог. Красный билд — старый модуль живёт, ошибки компиляции в `logs`. **Legacy dylib-хостинг (`REDLILIUM_GAME`):** тёплый reload между кадрами — сцена восстанавливается из снапшота, undo/selection сбрасываются, entity id меняются, после reload начинайте со `state`. Статический хостинг без behavior_reload — ошибка (Tier 2: перезапустите бинарь) |
| `play` | — | ack = запрос принят; между кадрами собирается **play-мир** — полная игровая композиция (та же, что в standalone-билде) из захосченной игры (статически слинкованной в game-owned бинарь редактора, ADR-037, либо `REDLILIUM_GAME`-модуля), стартовая сцена = текущая сцена редактора (или меню игры, если сцена не открыта). Пока сессия жива, `screenshot` снимает камеру play-мира; `state`/`inspect` продолжают читать мир редактирования |
| `pause` / `resume` | — | ack; пауза = игровые расписания не тикают (игровое время заморожено), а в play-мир инстанцируется инспекционный оверлей: EDITOR-сущности мира редактирования (данными, с флагами) + облётная камера — `screenshot` на паузе снимает её. Resume сносит оверлей целиком; поза облёта переживает паузы как значение |
| `stop` | — | ack; play-мир дропается целиком, мир редактирования не был затронут |
| `restart` | — | ack = запрос принят; Tier-2 exec-restart (ADR-037): редактор пишет session carry (текущая сцена + поза камеры) в `.redlilium/session.ron`, сворачивает цикл и exec-ает свежий бинарь с теми же argv. Соединение рвётся — переподключайтесь по пере-опубликованному `.redlilium/editor.port` (unix: PID сохраняется, это exec). Несохранённые правки сцены, undo и selection не переживают; в оконном редакторе запрос проходит через диалог unsaved changes |

Координаты пикинга — в **пространстве картинки сцены** (те же пиксели, что
выдаёт `screenshot`): агент смотрит на скриншот и тыкает в него. Резолв через
entity-index GPU-пасс (кадром позже); в headless пасс поднимается только на
время запроса.

Скриншот делается GPU-ридбеком текстуры сцены через frame graph (бинарь в
протокол не заходит — редактор пишет PNG в файл и возвращает путь).

`step` — это tick-on-demand: в headless-режиме команда **прогоняет** N кадров
(без неё простаивающий редактор кадры не крутит); в оконном режиме кадры идут
сами, и `step` вырождается в `wait(for: "frames")`. `shutdown` закрывает
редактор без диалога о несохранённых изменениях.

## Headless

`REDLILIUM_HEADLESS=1` запускает редактор без окна, свапчейна и egui
(remote-канал включается автоматически). Сцена рендерится в оффскрин-таргет
камеры фиксированного размера (`REDLILIUM_HEADLESS_SIZE=WxH`, по умолчанию
1280x720) — `screenshot` работает как в оконном режиме. Ядро общее
(`editor/src/core.rs`): тот же мир, те же EditAction'ы, та же история undo;
оболочки (`editor.rs` / `headless.rs`) отличаются только вводом и композицией.

Кадры тикают по требованию: пока есть незавершённая работа (запаркованные
ответы, `step`, занятый ассет-пайплайн) цикл крутится с фиксированным
dt = 1/60; после нескольких спокойных тиков он блокируется на транспорте до
следующей команды. Простаивающий headless-редактор не жжёт CPU/GPU.

## CLI

`cargo run -p redlilium-editor --bin editor_ctl -- <cmd> [...]` — сахар над
протоколом (см. шапку `editor/src/bin/editor_ctl.rs`). Одна команда — одно
соединение — одна строка ответа. `raw '(…)'` шлёт произвольный конверт.

## Эволюция

Протокол версионируется числом в `hello`; развитие аддитивное. Зарезервировано
на следующие срезы: `input` (инъекция ввода в play-мир), `drop_asset`,
инспекция play-мира (remote-канал, направленный на игровой мир).

## Реестр действий

Планка «любое действие AbstractEditor доступно через канал» реализована
реестром (`redlilium_ecs::ui::ActionRegistry`, ресурс мира): запись — это
`имя → конструктор из натурального RON`. Команда `action(name, params)`
строит действие и толкает его в ту же очередь → историю, что и UI; `actions`
возвращает реестр с usage-строками (агент строит вызов по ним).

Встроено (авторинг сцены): `spawn_entity` (новая сущность с
Transform/Visibility, опционально имя и родитель; **ответ несёт id созданной
сущности**), `delete_entity` (поддерево, undo восстанавливает),
`reparent`, `add_component` / `remove_component` / `set_component`,
`select`; (авторинг ассетов): `set_asset_settings` / `set_asset_reference` —
undoable правки записи DB, адресация по guid-строке, hot reload и
персистенция идут через apply. Шеллы и игровой код регистрируют свои
действия рядом (`ActionRegistry::register`); undo-состояние действие
захватывает в `apply`, поэтому конструктору нужны только wire-параметры.

 Id сущностей стабильны в рамках сессии, но не через undo/redo: после
undo+redo спавна сущность получает новый id (ответ команды его уже не
знает — перечитай `state`).

## Авторинг ассетов

`new_asset` создаёт файл + запись в DB (как «New asset» в браузере ассетов;
файловые операции вне истории — undoable только правки записей).
`set_asset_settings` меняет содержимое (цвет материала и т.п.),
`set_asset_reference` — ссылки записи. `save_prefab` / `spawn_prefab`
замыкают цикл: собрал сущность → сохранил как префаб → респавнишь где
нужно (spawn undoable, ответ несёт новые id). VFS-чтение/запись префабов и
файлов — блокирующие (локальные маунты; один кадр).
